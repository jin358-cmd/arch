# 建築施工流程系統 UI 簡化盤點（Phase 1）

盤點分支：`feat/simple-ui-v2`  
基準版本：`5a6bdf2`  
範圍：只盤點與規劃，不修改 UI、不變更 Supabase Schema、不刪除功能、不合併 `main`。

## 現況摘要

- 系統是 `index.html` 單頁應用，沒有 Router 或獨立頁面 Route；介面、資料常數與互動大多集中在同一檔案。
- 現有首頁同時放置專案管理、工期預算、四種進度檢視、四階段流程、核定審查、衝突檢核、會議及廠商明細，資訊密度過高。
- 專案先存瀏覽器 `localStorage`，登入後由 `supabase-sync.js` 同步；會議附件另用 IndexedDB 及私人 Supabase Storage。
- 既有同步、進度加權、方案鎖定及三層甘特圖邏輯可保留，本次應以導覽與呈現重組為主。
- 目前沒有獨立的每日施工紀錄、現場照片、缺失／異常及通用文件庫資料模型；資料部分散落在施工小項、查驗備註、衝突檢核與會議附件。

| 廠商／施工小項 | `building-vendor-v2-*` | 廠商管理與現場管理共用原資料 |
| 核定審查 | `building-practice-gates`、自訂核定資料 | 里程碑與待確認摘要直接引用 |
| 衝突檢核 | `building-practice-conflicts`、`building-custom-conflicts` | 未完成摘要進總覽，完整清單進更多 |
| 會議 | `building-practice-meetings`、`building-custom-meetings` | 專案資料保留完整紀錄 |
| 會議附件 | IndexedDB、本機快取、Supabase Storage | 保留；專案資料入口直接引用 |
| 每日施工紀錄 | 無獨立來源；部分存在小項日期／備註 | 第一版先彙整既有欄位，不新增資料表 |

| 缺失／異常 | 分散於查驗、風險與衝突檢核 | 第一版彙整既有待改善資料 |
| 圖面／合約／報價等 | 無集中來源，目前僅有會議附件 | 先建資訊架構；持久化方案另行驗收 |

## 第二階段建議邊界

1. 建立同頁四大入口，不導入新框架或 Router。
2. 專案總覽只讀取既有資料計算摘要，不建立重複資料。
3. 施工進度沿用甘特圖與三個次要檢視，階段篩選放入同區。
4. 現場管理第一版只重組小項、日期、進度、查驗備註與未完成檢核。
5. 專案資料第一版搬入會議與會議附件；其他文件先使用空狀態，不改 Schema。
6. 工期預算、完整廠商、跨階段檢核及同步／歷史收進「更多」。
7. 新 UI 使用狀態映射層，不直接更改底層既有狀態值。

## 風險與驗收前置

- `index.html` 同時承載大量 CSS、HTML 與行為，第二階段需小步重組 DOM，避免破壞事件與同步。
- 今日施工只能由既有小項日期推導；沒有日期時顯示空狀態，不杜撰內容。
- 落後狀態沿用方案鎖定基準；未鎖定時標示「尚無核定基準」。
- 正式缺失單、照片與責任期限需要新資料模型，未確認前不實作。
- 通用文件若要跨裝置同步，後續需設計 metadata 與 Storage 分類，超出第一階段。
- 第二階段每次改動均須驗證舊專案載入、同步鍵完整、四種檢視一致，以及手機 360–430 px 不爆版。

## Phase 1 結論

現有核心資料與運算可保留，適合採約 70% 既有邏輯加 30% 介面重組。主要問題是所有功能堆疊在同一首頁。第二階段應先以四大入口重新分配現有功能，再依驗收決定是否為照片、缺失與通用文件新增資料模型。
