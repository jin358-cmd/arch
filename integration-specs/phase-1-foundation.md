# Canonical Identity Phase 1 Foundation

## Implemented safe foundation

- `src/project-domain.js` defines canonical UUID validation, NFC + trim project-name validation, the 200-character limit, roles, permissions, immutable identity handling and canonical route construction.
- `src/legacy-project-adapter.js` is a pure compatibility layer. It never writes localStorage, IndexedDB, Supabase or Storage and never generates a canonical mapping implicitly.
- Known AI工程管理 test/template identity and all approved Atlas demo/seed/verification identities are explicitly excluded from automatic migration.
- Legacy text IDs remain readable only through an explicit `LegacyProjectIdentity` mapping. Synchronization must preserve an existing canonical UUID.
- These modules are not wired into the Production UI in Phase 1, so existing workflow behavior remains unchanged.

## Approved owner invariant

The existing canonical identity specification already requires both `projects.owner_user_id` and exactly one matching OWNER membership. Future schema and RLS must enforce their consistency transactionally. Owner transfer is an audited owner-only operation; direct client mutation of either side is forbidden.

## RLS contract draft (non-executable)

All future canonical tables are authenticated-only with RLS enabled and forced. Authorization derives from `auth.uid()` plus active `project_memberships`; request payload roles or user-editable JWT metadata are never authoritative.

- Project/member reads require an active membership.
- Project edits require OWNER or MANAGER; owner identity changes require OWNER and an audited owner-transfer command.
- Membership reads require project membership. OWNER may manage all roles; MANAGER may manage only MANAGER/EDITOR/VIEWER and cannot create, remove or replace OWNER.
- EDITOR and VIEWER cannot mutate membership. VIEWER is read-only except its own notification preferences.
- UPDATE policies require both `USING` and `WITH CHECK`; `TO authenticated` alone is insufficient.
- Helper functions, if later required, belong in a non-exposed schema, default to security invoker, and must not become public privilege-bypass endpoints.

## Migration draft status

No executable migration file was created. The local Supabase CLI is unavailable, and the project safety rule requires migration filenames to be generated by `supabase migration new`. The future migration must be additive: create canonical `projects`, `project_memberships`, and `legacy_project_identities`; preserve all workflow tables and text IDs; add no Project Name unique constraint, destructive conversion, drop, data move or Storage mutation.

## Approved decisions

### Project name uniqueness

Decision 8 approves duplicate normalized names. Names are labels, not identity; use UI disambiguation and duplicate warnings rather than a database uniqueness constraint.

### Unauthenticated project creation

Decision 9 requires login-first Formal Project creation. Unauthenticated users may create only namespaced Draft/Template objects. Promotion is authenticated and idempotent, creates a new canonical UUID, preserves Draft identity, and records `promotedProjectId` only after owner/membership and imported data pass validation.
